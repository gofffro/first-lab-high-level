## Анализ тестопригодности

После лабораторной №4 проект разделён на domain, application, адаптеры и configuration. `DefaultCheckAccessUseCase` получает узкие интерфейсы через конструктор: зависимости можно заменить тестовыми функциями без файлов, сети и стороннего mocking framework. Доменные политики детерминированы. Для новых модульных тестов не требуется менять правила доступа.

| Компонент | Что проверяем | Изоляция и сложности |
|---|---|---|
| `DefaultCheckAccessUseCase` | Все исходы, порядок ошибок, отсутствие последующих обращений при отказе, передача параметров, границы лимита | Собственные test doubles для всех семи зависимостей; нет зависимости от реальных паролей, данных и SHA-256 |
| `RegexResourcePathValidator` | Сегменты длиной 1–20, точки, буквы/цифры/подчёркивание, запрещённые символы, пустой путь | Чистая функция, прямые проверки |
| `NonNegativeVolumeValidator` | Ноль, границы Int, переполнение, отрицательные числа и некорректный текст | Чистая функция; фиксируем также существующее принятие `+10`, `0007`, `-0` |
| `DefaultActionParser` | Все три действия, смешанный регистр, неизвестные значения и пробелы | Чистая функция; пробелы по текущему контракту не удаляются |
| `PrefixPermissionPolicy` | Наследование по уровням, точное право, запрет соседей/родителей, различие `A` и `AB`, действие | Пользователи создаются внутри тестов, проверяется правило предметной области |
| Memory repositories | Точное совпадение ключа, отсутствующая запись, нулевой лимит, отсутствие наследования лимитов | Небольшие локальные Map; нет базы данных |
| `Sha256PasswordHasher` | Известные SHA-256 векторы, порядок salt/password, UTF-8, изменение соли/пароля | Реальный JDK MessageDigest; ожидаемые векторы заданы константами, Unicode-вектор получен независимо через .NET |
| `CliParser` | Обязательные опции, порядок, повторный вызов, справка, сохранение исходных значений | На каждый вызов создаётся новый ArgParser. Неверный синтаксис нельзя безопасно вызвать внутри JUnit: библиотека завершает JVM |
| `CliController` | Передача всех полей и возврат любого статуса без изменения | Fake входного порта, проверка единственного вызова |
| `CliResultPresenter` | Отображение всех восьми статусов в прежние коды | Прямые параметризованные проверки |
| `HelpPrinter` | Точный текст и один вызов вывода | Внедряемая функция вывода вместо глобального перехвата System.out |
| `run` | Делегирование, возвращаемые коды, справка при пропущенных опциях, отсутствие вызова use case при справке | Fake use case и локальный буфер вывода; `exitProcess` не вызывается |
| `CompositionRoot`, `DefaultData` | Корректность связей и реальных учётных данных | Отдельный integration-набор; это не модульные проверки |

## Изменения для тестирования

1. `HelpPrinter.print` принимает `output: (String) -> Unit = ::println`. `run` принимает такой же аргумент и передаёт его в печать справки. По умолчанию вывод тот же; тесты используют локальную коллекцию. Глобальные потоки, состояние JVM и порядок тестов не меняются.
2. Добавлен каталог `tests/` с тестами JUnit Jupiter и параметризованными сценариями. В unit-тестах use case используются test doubles, а не реальные адаптеры.
3. Зависимости скачаны готовыми JAR в `lib/`, версии закреплены. Для IDEA добавлены API, Engine, Params и их зависимости; для терминала используется Console Standalone. Контрольные суммы проверяет `scripts/setup-libs.sh`.
4. Скрипты перенесены в `scripts/`, Markdown-документы — в `docs/`. Добавлены отдельные команды компиляции и запуска тестов; Gradle/Maven не вводились. Пути считаются относительно скрипта, classpath учитывает Windows/Linux.
5. Локальный `.iml` настроен на `tests/` и JUnit Test scope. Настройки IDE не включаются в PR; инструкция для нового клона есть в [README](README.md).

Бизнес-логика, тестовые учётные данные, текст справки, приоритеты ошибок и коды завершения не изменены.

## Что не тестируется отдельно и почему

- `main` не вызывается из JUnit, поскольку завершает JVM. Реальный вход, упаковка `app.jar`, загрузка `kotlinx-cli` и коды процесса проверяются CLI-регрессией.
- Синтаксические ошибки внутри `ArgParser` проверяются отдельными процессами по описанной выше причине; исходный код сторонней библиотеки не изменялся, приватные/internal API не используются.
- Автогенерируемые `equals`, `hashCode`, `copy` у `User`, `AccessRequest`, `CheckAccessCommand` и enum не имеют отдельных тестов: собственной логики в них нет. Сами значения участвуют в проверках use case и контроллера.
- Интерфейсы портов не содержат исполняемой реализации; проверяются их реальные адаптеры и взаимодействие со сценарием.
- Графический запуск JUnit в IDEA и работа Linux/WSL в этой среде не проверялись. Здесь выполнены консольные bash-скрипты на Windows; инструкция настройки IDEA и обработка разделителей classpath добавлены.
- SonarCloud и процент покрытия не заявляются: эта работа проверяет поведение, а не подключает ранее запланированный внешний анализатор.

## Подготовка к TDD

Для последующего изменения сначала добавляется тест нового правила и запускается один класс:

```bash
bash scripts/test-unit.sh --include-classname '.*VolumeValidatorTest'
```

Затем проверяется ожидаемое падение (Red), вносится минимальная реализация до успешного запуска (Green), после чего упрощается код (Refactor) и выполняется весь `bash scripts/test.sh`. Новое правило должно быть согласовано отдельно: текущие тесты фиксируют существующий контракт. Test doubles позволяют писать такие проверки без подготовки реальных учётных записей или изменения `DefaultData`.
